# AI 几何沙盒（Geometry Sandbox）

给智能体一张**任务卡**和一个**模型文件**，它自己观察、自己选工具、自己判断证据够不够、
自己提交并接受审计。仓库里没有针对某道题写的代码：题目只以文本（card）存在，
判断只以决策记录（episode）存在，数值只由几何内核产生。

## 两条执行路径，别混淆

| 入口 | 谁在决策 | 用途 |
|---|---|---|
| `run.py` | 外部写好的 `plans/*.json` | plan 执行器。用于回归基线、复算数值 |
| **`run_agent.py`** | **沙盒内的 agent（`agent/loop.py` + `agent/policy.py`）** | **参赛形态：没有预先解好的 plan，只有观察→决策→执行→复核的循环** |

`run.py` 存在的意义是对照组：同一套工具，一个由外部指令驱动、一个由 agent 自己驱动，
两者数值必须一致 —— 这证明编排层没有引入偏差，也证明工具层是确定性的。

## 一条命令复现

```bash
bash reproduce.sh
```

造 4 个变体 → 用 `run_agent.py` 跑 agent（含录像）→ 跑 2 个对抗样本 → 生成 `runs/agent_matrix.md`。

写层（改模型）+ 读层（只出数字）共用一条命令，跑完自动做独立验收：

```bash
python run_edit_all.py          # 读层 03/02/04/09 → 写层 07/05/06/08/10 → 验收
python run_edit_all.py --only 03    # 单独跑一道
python run_edit_all.py --skip-run   # 只重跑验收（读已有产物）
```

先读层再写层是有意的：读层只出数字、不出文件，跑完能立刻看出测量侧（截面、体积、
接触、包含）可不可信；一旦测量侧错了，写层的失败会伪装成「编辑没做对」，故障点就混了。

最后一步 `verify_edits.py` 用评委的立场写：**不读智能体的报告**，只认磁盘上的东西 ——
写层题把 `runs/edit0*/` 下的 12 个模型文件读回来，用只读工具重量，再对照任务卡逐条勾；
读层题没有产物文件，就只读 `result.json` 里提交的数字，用**另一套算法**重算一遍
（球冠解析式 vs 辛普森积分、球缺闭式解 vs 二分反解、行列式体积 vs 网格积分）。
期望值来自原始模型与题面给的坐标，不是抄答案。共 90 项检查（89 通过 + 1 已知限制）。

其中「会不会撞上」这类结论不复用碰撞内核：`verify_edits.py` 里另写了一套分离轴粗筛 +
边穿面定案的判定，按 0.1° 定点逐格重跑一遍开门扫掠，和智能体的答案交叉核对。
两套实现同时错到同一个数上的概率，远低于一套实现自己错。

换输入再跑一遍（格式 / 命名 / 单位 / 90°），看写层是不是只对 IFC 有效：

```bash
python compare_edits.py         # → runs/edit_matrix.md
```

单次运行 agent：

```bash
python run_agent.py --card tasks/T01_2.md \
                    --model ../pkg/AI-Geometry-Models/IFC/AI_Geometry_Input.ifc \
                    --episode episodes/T01_2.agent.json --tag ag_ifc
```

三种决策策略，接口相同（`agent/policy.py`）：

| 策略 | 命令 | 说明 |
|---|---|---|
| `RecordedPolicy` | `--episode episodes/…json` | 回放已记录的决策序列。**没有 API key 也能跑**，逐条对照「当时的观察 → 当时的判断」 |
| `LLMPolicy` | `--llm gpt-4o` | 运行时真调 LLM（OpenAI 兼容，`LLM_API_KEY` / `--base-url`）。生产路径，编排层与工具层一行不改 |
| `FallbackPolicy` | `--fallback` | 无 key 无记录时的规则回退。只证明架构能起来，会诚实地停在「证据不足」 |

## 控制台：在页面上出题（`studio.py`）

观测台证明「跑出来的东西可信」，控制台回答另一个问题：**换一道题，它还能不能自己解**。
所以这里必须真写盘、真调工具 —— 两个进程刻意分开，`view.py` 的只读承诺不被稀释。

```bash
python studio.py                    # http://127.0.0.1:8770/  （Ctrl-C 退出）
python studio.py serve --port 9000
python studio.py export --runs ag_ifc,edit09,edit02   # 单文件快照，双击即看
```

页面两张，hash 路由：

| 路由 | 内容 |
|---|---|
| `#/` | 赛事要求怎么读（输入只有两样东西 / 答案要能追证 / 写层交文件 / 换皮还成立）、七阶段与三层架构、能力面（度量/关系/运动/写层各自做到哪一步）、40 个工具（点开看前置条件、返回物、降级路径） |
| `#/lab` | 三栏实验场：左=工具映射，中=出题与过程，右=画面/读写层/答案 |

`#/lab` 三栏各自解决一件事：

- **左：工具映射。** 40 个工具按「它回答什么问题」分五组，右侧是这一轮的实际调用次数；
  agent 调到哪个，哪个亮起来，回放游标走到哪也跟到哪。点一行 = 只看这个工具的调用。
- **中：对话与过程。** 顶部是出题入口（一段自然语言 + 模型下拉/上传），下面是逐步的「为什么 + 参数 +
  返回摘要」。阶段条显示各阶段条数，点击跳到该阶段第一步；底部回放条有播放/单步/拖动/倍速/
  全部-逐条，以及 **存档 / 读档 / 新一轮**。
- **右：三张可折叠卡。** 几何画面（实时三维 + 步骤标注 + 焦点相机，见下）、读写层
  （读层测量 / 写层改前改后与产物）、答案（值 + 审计 + 证据步骤 + 自然语言回答）。点标题折叠，三张互不影响。

**几何画面**用 three.js 实时渲染：可拖/滚/平移/点选实体，**步骤标注（marks）**把每步工具
做了什么画在三维上（测量线、角度弧、切面、标记点），底部时间线滑块逐帧回看；
**相机跟随焦点实体**（焦点占画面约 75% 且居中，其他构件半透明）。细节见下「几何画面」一节。

**出题入口只有两样东西**：一段原话、一个模型文件。没有模式开关，也没有「选一道题」的列表 ——
控制台不认识任何一道题（`studio.py` 里没有题目表，`/api/home` 也不返回题目）。

「这段话要什么」由 **`agent/brief.py` 当场编译**：

```
原话 ──compile_brief──> 本轮任务规格（交付类型 / 要交的量 / 题面点名的实体 / 原话自带的约束）
                        └──render_prompt──> 注入 system 的说明
```

规格是**中间产物**：写进 `runs/<tag>/brief.json` 跟着这一轮一起存档，页面上以「管线编译」卡片摊开，
可以逐条核对它把原话读成了什么。它不是要人填的表单 —— 让人填字段，等于把「读懂题目」这一步
替 agent 做掉了；而这一步正是要考的东西。

抽取是规则、不是第二次 LLM 调用：输入什么、抽出什么可逐条复现；读不出就不列
（认不出交付类型就退回「按原话执行」），宁可少写，也不在题目之外替 agent 补一句判断。

跑一轮的决策走在线 LLM（DeepSeek `temperature=0`，70 轮 / 900 s 预算）。
不收敛就是 `STALLED` / `BUDGET_EXHAUSTED`，不伪装成成功。

**实测（都是现场输入，没有预置答案）**：

| 输入（一段原话） | 结果 | 出来什么 |
|---|---|---|
| 「这个模型里有一个球，请给出它的半径、球心三维坐标，以及按理想球体计算的体积。」 | `OK` · 24 轮 · 43.5 s | r = 1.0 m，球心 (−8.3, 0.0, 1.0)，理想体积 4.1888 m³（拟合残差 3.4e-7） |
| 「所有实体，一共有几个，哪几个是落地的，每个实体的包围盒长宽高。」 | `OK` · 31 轮 · 64.0 s | 20 个；落地 10 个（判据 `z_min = 0`，地面板 C004 在 −0.12 不计入）；20 组包围盒尺寸 |
| 官方 Task 03 原文（四问：房间净尺寸/洞口、地板面积、球与正方体体积、1 m² 截面高度） | `STALLED` · 53 轮 · 121 s | 没有交出答案：40 步耗在 IDENTIFY，最后卡在对同一面墙重复切截面（第 6 次相同调用被判停滞） |

判据不是「跑完就算」：上面前两轮都是 `audit_reject = 0`，即每个交出去的数字都能指回某一步工具返回。

第三行是**没做成**的那一条，写在这里而不是藏起来：四问合并成一段话以后，agent 在识别阶段
（哪面墙、哪个是门扇、洞口在哪）就烧掉了全部预算，从未进入测量。它暴露的是「多角色识别」
这个已知短板，不是输入形式的问题 —— 单独问其中任何一问（如前两行）都能收敛。

存档是自包含 JSON（`kind=hack26.studio.run`）：run 的账本、观察、答案，加上全部帧的 base64。
读档后就地回放，不依赖服务端。另外两个入口：`#/lab?tag=edit09` 直接打开某一轮，
`#/lab?live=<tag>` 接管正在跑的一轮（页面会继续轮询）。

跑一轮的成本：40–90 s（含渲染）。控制台写的 run 落在
`runs/live_<月日_时分秒>/`，与 `run_agent.py` 命令行产生的完全同构，`view.py` 照样能看、能导出。

## 人怎么看这个过程（观测层）

沙盒是无人值守跑的，所以「过程」必须能被人当场复核，否则录像只是装饰。四条通道，全部只读
（不触发任何工具、不需要 API key、不改 runs/ 一个字节）：

| 形式 | 命令 | 用途 |
|---|---|---|
| 终端列表 | `python view.py ls` | 所有 run 的状态 / 轮次 / 答案一行一个，`--kind all` 连开发记录一起看 |
| 终端时间线 | `python view.py show ag_ifc` | 逐步打印「阶段 · 步骤 · 工具 · 为什么」，`--full 400` 附带原始观察 |
| 本地观测台 | `python view.py` | 起 `127.0.0.1:8765`：左选 run，中间逐步回放，右侧画面随步骤切换 |
| 单文件导出 | `python view.py export ag_ifc` | 生成 `runs/ag_ifc/viewer.html`，**双击即看**，不起服务、不装依赖；加 `--inline` 连帧一起内嵌，得到一个可随手带走的 HTML |

写层的运行在观测台里有专门位置：时间线上「几何已改」「读回自己的产物」各自成一种醒目的条，
右侧多一张 **写层（EDIT）** 卡片，把每个实体改前/改后的尺寸与体积并排列出
（`C001 2.5×2.5×2.5 → 2.5×2.5×3.0`，`15.6250 → 18.7500 +20.00%`），
下面列出这次写出去了哪几个文件、各多少字节。这些数字全部取自只读体检工具，不是编辑函数自报。

读层的运行换成 **读层（READ）** 卡片：一次测量/判据一行，按工具类型只挑那个工具要回答的那几个数
（`sphere_region` → 关系 + 有符号间隙 + 内外体积；`contact_area` → 面积 + 共面三角形对数；
`contains` → 平面 + 内外计数 + 最小余量；`solve_section_height` → 反解高度 + 是否单调 + 二分次数）。
读层四题的答案是嵌套的（五组位置关系、三面墙、16 个实体），答案面板会把它们摊成小表 ——
早先这里直接 `String(v)`，读者只能看到一串 `[object Object]`。

观测台读四份既有产物，不为展示多写一份数据：`events.jsonl`（账本：谁在哪一步做了什么、为什么）、
`steps.json`（每步的完整观察）、`frames/manifest.json`（每帧属于哪一步）、`result.json`
（答案 / 审计 / 门控 / 失败升级）。

四个刻意的设计：

1. **画面跟着步骤走**。`manifest` 的每帧带 `steps`，游标落在第 N 步就切到该步所属镜头 ——
   不是播一段视频，是「这一步 agent 看到的几何」。`run_agent.py` 里为此把 step id 写进了场景。
2. **数字可追**。答案面板里每个距离点一下，跳到**第一次出现这个数**的那次工具返回；
   审计规则（1e-6、必须出现在证据步骤里）在界面上被复述一遍，看的人不必读源码。
3. **失败面不藏**。`GATE_BLOCKED` / `AUDIT_FAILED` / `STALLED` 各有可读解释；被拒的数字逐条列出
   （例：「这些数字无法追溯到任何证据步骤：[0.42, 1.85, 3.1]」）。
4. **账本在界面上自检**。逐条核对 `prev` 是否等于上一条 `hash`，断了标红 —— 改一条记录就会露。

## 编排层做了什么（这是比赛要的那部分）

`agent/loop.py` 只 300 行，但它决定 agent 是不是「会解题」：

| 机制 | 位置 | 为什么必须有 |
|---|---|---|
| **七阶段门控** | `PHASE_TOOLS` | SURVEY 阶段调不了 `distance`，REPORT 阶段调不了 `select`。越界被拒并留痕 `gate_reject`。**从结构上排除「跳过识别直接答题」**。第七阶段 `REVALIDATE` 的白名单里**没有编辑工具**，见下一节 |
| **步骤语义标签** | `_call(label=…)` | 引用用 `@win.items` 而不是 `@s4.items`。失败恢复多耗几轮也不会让引用错位；证据清单变成可读的一串名字 |
| **观察压缩** | `agent/schema.observe` | 只对「长清单的元素」做字段白名单，嵌套元信息保持完整。工具输出原样灌给 LLM 会让它淹没后开始编 |
| **失败升级而非退出** | `_enter_recover` | `expect_n` 不符 → 进 RECOVER，把诊断交给策略自救，成功后 `failure_resolved`。45° 变体就是靠这条自愈的 |
| **换路径也能消解失败** | `_resolve_reason`（判据是纯函数，`selftest.py` 单测） | 三条路径：同工具补对（`same_tool`）、换工具但**条数到位且原来那几件仍在结果里**（`superset`）、RECOVER 里换路径（`recover_move_on`）。`superset` 是为「一条 count_mismatch 永远挂着」写的：T09 用 `select` 凑不齐 3 个门框料，后来用 `clusters` 从另一条路径证明就是 3 件，旧规则只认同工具 → 门控拒 24 次 → 89 轮 / 1.89 M tok；改完同样场景 43 轮 / 1.02 M，0 次拒绝、0 步 RECOVER |
| **答案审计** | `_audit` | 提交的每个数字必须能在某个证据步骤的输出里真实出现过（1e-6 相对容差）。**「编一个看起来合理的数」在结构上不可能通过**。空 `values` 直接拒：它曾经换来一个绿色的 `OK`（T09 有一次 54 轮后交 `{}`，因为审计只管「数字有没有出处」，什么都不写就天然通过）。量不出来应该走 `declare_insufficient`，那是诚实的终态 |
| **语义标签的审计** | `_audit` + 族 facts | 答了「门 / 窗 / 落地窗 / 无法区分」，标签必须落在该族 facts 允许的范围里（范围由 grounded、下框、扇推出），且 evidence 里必须引用算族的那一步。**「标签是证据的结论」，不是形容词** |
| **预算 / 停滞** | `max_turns`(声明) + `hard_turns`(终止) / `_sig_count` | **两层预算**：`max_turns`是声明预算，驱动收口提示与策略里 budget_left（剩余 ≤15% 时催交卷）；`hard_turns`（默认 max_turns×1.5）才是真正硬停判据，容错区 `[max_turns, hard_turns)` 让"就差一两轮"的任务跑完，最终状态打 `BUDGET_OVERRUN`（非纯失败，供事后减分）。`--grace-turns`/`--grace-wall`可显式配置容错额度。收尾状态按「被什么挡住」命名：`OK`/`GATE_BLOCKED`/`AUDIT_FAILED`/`BUDGET_EXHAUSTED`/`BUDGET_OVERRUN`/`STALLED`。几何被改过之后签名计数清空 —— 「改前量一次、改后量一次」是写层最该做的动作，不能判成原地打转 |
| **语义记忆 facts / 结果 memo** | `loop._extract_facts` / `loop._memo_result` | **过程可压缩、结论必须保留**。观察滑出 `keep_full=4` 窗口会被压成一行表格，若只存原始观察，语义结论（哪面墙是门墙、哪个是框）就跟着丢 —— agent 推出「门墙是 C005」后算夹角又用 C006，自己跟自己矛盾（实测 T01-3 答 25°≠65°）。`_extract_facts` 从 `openings`(grounded/sill_z)、`assembly`(wall/grounded/opening)、`select`(dims 最薄边>0.05m=框) 提炼参照物身份判据，固化进 `self.facts`；`_memo_result` 每步核心结论提炼成结构化 JSON。两者每轮随 `ctx` 传给 LLM（`policy._messages` 渲染「已确认的语义事实，不要推翻」）。**只做搬移+标准化，不替 agent 选词** |

## 写层（EDIT）：改完必须落盘再读回

前四阶段把模型读成数字；写层的任务反过来，要**改出一个新的模型**。这里最容易糊弄的地方在于：
编辑函数自己就能返回「改完之后体积是多少」。如果直接把这个数写进答案，整条链就成了自证 ——
工具说自己改对了，然后就没人再问。

所以写层加了两条无法绕过的纪律，每条都由阶段机强制：

| 纪律 | 实现 | 被违反时会怎样 |
|---|---|---|
| **改了就落盘** | `EDIT` 阶段的门控是 `(not edits) or bool(emitted)` | 动了几何却没有 `emit` 写出文件，离开 EDIT 阶段被拒 |
| **落盘就读回** | `REVALIDATE` 的门控是 `bool(reloaded & emitted)` | 读回的文件不是自己刚写出去的那个，进不了 REPORT；`REVALIDATE` 的白名单里没有编辑工具，想边改边复核也不行 |

`load` 一个文件不算复核，**只有读回自己写出去的那个路径**才记 `reloaded_own_output`
（拿原始模型重读一遍是看没改过的东西）。落盘格式为单文件 glTF（内嵌 base64 缓冲）或 OBJ，
读回时沿 `asset.extras.unit` 恢复单位，不走对角线先验。

四条编辑原语，全部与任务无关：

| 工具 | 做什么 | 用在 |
|---|---|---|

这套体检在编辑时做一遍、读回后再做一遍，两边必须一致。

## 运动层（MOTION）：会不会撞上，以及凭什么说没撞

08 与 10 问的不是「距离多少」，而是「**整个过程**里有没有一处穿进去」。这类问题最容易
在两个地方翻车：把「相切」当成「撞了」，或者只查起止两个位置就下结论。所以这一层把
判定拆成三种状态，每一种都有自己的判据：

| 状态 | 判据 | 说明 |
|---|---|---|
| **分离** | 相交三角形对数 = 0 | 两个实体的面包容盒都不交，直接免测 |
| **接触 / 相切** | 有三角形对相交，但无人进入对方 | 承托面贴在一起就是这一档。相切算相交（判分离用严格小于） |
| **重叠** | 边穿刺 > 0，或顶点侵入深度 > 1 µm | 真的穿进去了 |

两个穿透判据必须同时存在，各补一个盲区：

- **顶点侵入** 抓「实体块压进实心件」——插脚进槽、箭体压平台。查得到是因为压进去的那一方，
  顶点必然落进对方内部。
- **边穿三角面** 抓「薄板穿过细杆」——门扇穿过椅腿、隔板切过横档。这种情形**两边的顶点
  全在对方外面**，顶点判据一个都查不到；只有一条边割穿对方的面。

边穿刺还必须排除「擦边」：交点落在重心坐标内部还不够，还要离目标三角形三条边都有实质距离。
少了这一条，箭体底面压在槽壁顶边会被算成 104 对穿刺（实测踩过）。

**扫掠 = 粗扫 + 边界二分，精度必须一起报出来。** `sweep_rotate` / `sweep_translate` 的返回值里
带 `scan_step_deg` / `refine_deg` / `n_probes` / `method` / `limits`，因为「没查到」和「不存在」
是两件事：窄于步长的孤立接触会漏，连续段不会漏。这是一句必须写在答案里的限定，不是免责声明。

重叠区间的求法有个坑：**不能假设「段首相切、段尾重叠」**。08 的两种状态都是两端相切、
中间才穿进去，只看段首段尾会得出「无重叠」。正确做法是在每个相交段内做 K=9 点采样，
再对重叠子区间的两侧各二分一次。

## 形状层（SHAPE）：拆件、切截面、配对

10 要「三个插脚对三个凹槽」，而插脚与箭体焊成一个单连通实体（1278 个面、1 个连通分量），
按连通性拆不开。这一层的办法是**在给定高度切一刀，看截出几个闭合环**：

| 工具 | 做什么 | 用在 |
|---|---|---|
| `parts` | 按面连通性拆连通分量 | 先试一次，拆不开才知道必须走截面 |
| `levels` | 顶点沿轴向的高度分层（层高 + 顶点数） | 找特征平面：箭体底面 1.1 / 1.5、平台 0.0 / 0.17 / 0.6 |
| `profile` | 指定高度的截面环（面积、周长、边长、多边形、内环） | 在 1.15 / 1.45 切出三只插脚（0.3×0.2 / 0.2×0.28 / 0.24×0.17） |
| `pockets` | 上表面往下的平底凹陷（轮廓、深度、面积、中心） | 三个槽：0.208×0.308 / 0.288×0.208 / 0.178×0.248，深 0.43 |
| `regid2d` | 若干对应点 → 最优 2D 刚体变换（转角、旋转中心、平面平移、残差） | 三对中心点解出 40.000004°、残差 1e-6 |

三个设计细节，每个都是踩出来的：

1. **配对不靠编号、不靠位置猜测，靠截面指纹**。插脚面积 0.0600 / 0.0560 / 0.0408，
   凹槽 0.0641 / 0.0599 / 0.0441，降序一一对应；每对的边长都相差同一个 8 mm 装配间隙。
   编号是读入顺序的副产物，换一个文件就全变。
2. **多边形中心必须用面积质心，不能用顶点平均**。三角化会在直边中间插共线点，
   顶点平均被拽偏 2 cm —— 这个量级足以让「配对正确」变成「残差很大、怀疑配错」。
3. **`regid2d` 的平移要分平面分量**。三维的 `translate` 混着质心的轴向高差
   （插脚中心 1.15 与槽底 0.17 之差 = −0.98），拿它去做水平平移会把整支火箭压进平台 0.46 m。
   现在单独返回 `translate_plane`，沿轴分量恒为 0。

后 7 个（`sphere_region` `contact_area` `fit_sphere` `proj_area` `solve_section_height`
`calc` 与 `contains` 的 `plane` 参数）是补读层四题时加的，各有各的不可替代性：

| 工具 | 为什么非要它 |
|---|---|
| `sphere_region` | 球与盒的交体积没有现成工具能算：`collide` 只回答「插没插进去」，`distance` 只给最短距离。有符号距离还必须按**球面**量（`d_face − r`），按球心量会把「外切」报成 1.0 |
| `contact_area` | `distance=0` 有两种可能：贴合，或嵌在对方体内。面接触面积 = 共面三角形对的重叠面积之和，边/角接触天然为 0 —— 题面「仅有边角接触不算面接触」因此可以直接落成判据 |
| `fit_sphere` | 题面给「半径 1 的球」，网格实际半径要量出来才能算理想体积。代数最小二乘解 `\|p\|² = 2c·p + (r²−\|c\|²)`；报出的半径与理想体积必须用**同一个**取整半径算 |
| `proj_area` | 「占地面积」是投影的凸包面积，不是包围盒面积，也不是分层截面之和（后者会重复扣） |
| `solve_section_height` | 反解「截面积 = 1 m² 时的高度」。先预扫判单调，非单调要把所有跨越段都列出来，只对第一段二分 —— 直接二分一个非单调函数会得到任一个根，而不是「第一个根」 |
| `calc` | 派生量（剩余面积、差值、比值）必须由工具算出。报告里手写的减法和除法没有出处，审计会拦 |
| `openings` | 「洞口」不是构件，是构件上缺的那块料。它在文件里可能是独立的洞口盒，也可能只是墙上缺料 —— 按**面覆盖率**算缺料，两种情形一套算法。通底（门洞）与不通底（窗洞）由 `grounded` 分开 |
| `angle` | 平面之间的夹角要的是「较小夹角」，而两条法向的有向夹角常常是钝角（门扇 65° 的两法向夹角是 115°）。工具同时返回 `angle_deg / acute_deg / dot`，避免模型自己取补角时把 65 报成 115 |
| `select(probe=true)` | 「唯一命中」是必要条件不是充分条件，所以补了两个检验：**反例检验** —— 每条判据必须能点名「谁被它排除了」（某个候选满足其余条件、偏偏不满足这一条），指不出反例的是凑数条件；**余量检验** —— 阈值还能挪多少而不改变结论（正好压在某个候选的实测值上，说明这个「唯一」是巧合）。编排层在登记角色时还会顺手算一次反例覆盖，报告里显示成 `1/2 个角色的每条判据都能指出反例` |
| `assembly` | 「谁属于这个洞口」不能用重合度判 —— 重合是位置关系，门一开就不重合了。改用接触+连通：面接触（在洞口棱柱内）、线接触（贴洞口边界环，双向量：顶点→边界线 ＋ 边界点→构件面，否则门套这种「面压在边界线上」的件会被漏掉）、连通（玻璃经框、把手经扇）。开合于是退化成参数（扇平面与洞口平面的夹角），不是特例 |
| 指纹 `h_long_axis/h_long/h_short` | 比较 `sx` 与 `sy` 谁大，是纯几何结论，不需要判断力。不给这个字段，模型在旋转过的房间上会把短边当长边（实测：`d0` 仍是 4.8，但 4.8 已经从 x 换到了 y），随后左右/前后整套换算全反 |

`contains` 加了 `plane` 参数：判「占地是否在地板内」是**平面**问题，三维包围盒会把坐在
地上的椅子（z 0…0.9 超出地板 −0.12…0）判成越界。

每个工具都带**前置条件 / 失败时的降级路径 / 返回物说明**，三项一起进 LLM 的 tool schema。
注册表里不存在任何任务编号。

| 编排约束可被攻击测试 | `episodes/adv_gate.json` 试图跳过识别 → `GATE_BLOCKED` |
| 答案不可编造 | `episodes/adv_fabricate.json` 提交假数字 → `AUDIT_FAILED`，并逐条列出无法溯源的数值 |
| 每步可回溯 | `events.jsonl` 哈希链，改一字节即断链 |
| 换模型重跑不变 | `runs/agent_matrix.md`：格式/命名/单位/90° 全一致；45° 触发自救仍一致 |
| 写层不自证 | 编辑后必须 `emit` 落盘、必须读回**自己写出的那个文件**才能进 REPORT；`verify_edits.py` 用评委立场只读文件重量 |
| 读层不自证 | 读层四题没有产物文件，验收换成「换一套算法」：球冠解析式 vs 辛普森积分、球缺闭式解 vs 二分反解、行列式体积 vs 网格积分。同一份提交数字，两条路径同时错到同一个数上极难 |
| 碰撞不自证 | `verify_edits.py` 里另写一套几何判定（分离轴粗筛 + 边穿面定案 + 正反双射线内部判定），按 0.1° 定点重跑开门扫掠与反向抬升，与答案交叉核对；两套实现的差异范围也写进验收表 |
| 失效就说不知道 | 证据不足时 `status=INSUFFICIENT_EVIDENCE`，不给错数 |
| 录像即账本 | `frames/manifest.json` 记录每帧对应的阶段与角度，视频由帧编码，非录屏 |

控制台的出题入口只有一段原话和一个模型文件，没有「挑一道题回放」这个选项。
用在线模式审的是另一件事：同一套编排层换策略还能不能跑 —— 现在的答案是「能跑，但不稳定」。

**已稳定的部分**：椅子 `C017`、门扇 `C011` 每次都能压到唯一命中；`distance` 拿到 0.696547，
与我手算的基准一致；见证点残差 1e-7。协议层（引用、标签、门控、审计、账本）全程无异常。

**卡住的地方**（诚实的结论，不是调参问题）：

1. **框体 vs 内嵌板**。窗 = `C013`(框 1.4×1.4×0.24) + `C014`(玻璃 1.28×1.28×0.02)；
   画 = `C015`(框 1.2×0.9×0.08) + `C016`(板 1.04×0.74×0.025)。题目问「窗框 / 画框」，
   而内嵌板的尺寸特征更「干净」，模型很自然地选了板。要区分只能靠「框有贯通内环、板没有，
   且板嵌在框的内环里」这一条**关系判据**，而当前工具里 `contains` 只比包围盒，不够。
2. **它不擅长证伪自己的假设**。第 8 轮它认定「门扇应轴对齐」，理由是「门要么关着要么沿轴开」——
   而题面明写「打开的门」。这类错误不是工具缺失，是模型对几何情境的想象替代了读数。
3. **成本**：约 7.5k prompt tokens / 轮，80 轮 ≈ 60 万 tokens。回放路径 0.2 秒、0 成本，
   这就是为什么参赛提交以 `episodes/` 为主、LLM 路径作为「同一编排层可换策略」的证据。

**下一步要补的是工具，不是提示词** —— 这条判断后来被 T-09 验证了一半，也修正了一半：

- **被验证的**：补的确实是工具，不是提示词。`contact_area`（谁贴在哪面墙上）与
  `mesh_report.fill`（墙面填充率）两个量一加，窗与画框立刻分开了 —— 分水岭不是构件长什么样，
  而是**它贴的那面墙有没有洞**：窗贴 0.874 的墙（缺口 0.392 = 1.4×1.4×0.2），画框贴 1.000 的整墙。
  这两个数都是几何量，不需要模型对「窗应该长什么样」有任何想象。
- **被修正的**：当时设想的解法是「把 `contains` 升级成内环包含判定」，实际上没必要。
  「框有贯通内环、板没有」这条判据要求先做环-环包含，代价高且脆（内环方向不稳定）；
  而「归属 + 墙有没有洞」是**两个已有量的组合**，更短、更硬。玻璃嵌在窗框里、板嵌在画框里
  也确实用不着内环判定 —— 板严格在框的包围盒内，包围盒包含就够。

仍然没有的是 `enclosure` 这种「把框与其内嵌板自动配成对」的判据：现在这一对
（`glass_inside_frame` / `board_inside_picture_frame`）是逐对查的，实体一多就得手工枚举。

## 非实题用例：换问谁、换数值（`try_cases.py`）

赛题只有 10 道，跑通了也可能只是「这 10 道刚好合口味」。所以另有一套用例：
**同样的问法，换提问对象、换模型里的数值**，看流程还成不成立。

```bash
python try_cases.py                 # 跑全部（需要 LLM key），出表
python try_cases.py --only A C      # 只跑两例
python try_cases.py --truth-only    # 只算期望值，不跑 agent
python try_cases.py --report-only   # 只汇总已有运行 → runs/cases.md
```

期望值不是抄答案，也不是人记的：`roomtruth.py` 从**当前这个模型**当场重算 ——
门洞用「墙面顶点网格 + 三角形覆盖」算缺料（与 `openings` 两条实现），方位用
「右向＝门洞墙→它对面」「后向＝开口→有墙」，目标中心用顶点包围盒中点。
换一个朝向、换一个单位算出来的期望值必须一字不差，这本身就是一条自检。

| 用例 | 变的是什么 | 结果 |
|---|---|---|
| A 基准 · 问椅子 | 对照 | 一致 |
| B 换对象 · 问窗框 | 换一件东西问 | 一致（2.500 / 3.150） |
| C 换对象 · 问画框 | 换一件更容易混的东西问 | 一致（4.860 / 1.170）。收窄前 96 轮（37 次 select 硬筛），收窄后 51 轮且走了族 |
| D 换数值 · 椅子挪位 | 椅子平移 (0.6, 1.2)，现造变体 | 一致（1.400 / 1.870） |
| E 换单位 · mm | 坐标 ×1000 | 一致（0.800 / 0.670，答案仍是米） |
| F 换朝向 · 转 90° | 绕地板前左角转 90° | 一致（0.800 / 0.670） |

判定分三层：数值（±2 cm，框/玻璃/画心的中心本来就差 1 cm 量级）、标签、**标签与带符号偏移
是否自洽**。第三层是这套用例逼出来的：C/D/E/F 上都出现过「距离算对了、标签写反」——
那不是量错，是翻译错，混在一起就会把问题归错类。

C 例的失败很有价值：模型能算出窗的位置（数字全对），只是把「画框」认成了窗。
这说明瓶颈已经从「几何量」转移到「**题面指谁**」，正确解法是关系判据（贴的那面墙有没有洞，
Task 09 就是这么做的），而不是再加尺寸阈值 —— 加尺寸只会让它换一个认错的对象。

顺带抓到一只不报错的 bug：同进程连读两个模型时，指纹缓存键是 `(sid, id(S))`，
而 `load` 换场景后旧对象被回收、新对象可能拿到**同一个 `id()`**，于是第二个模型读到第一个模型
的指纹（表现为「旋转模型的椅子坐标是原件的」）。现在键里带场景代号 `bus.gen`，
`load` 与编辑替换都会 `touch()`。这类 bug 不抛异常，只让结论错位 —— 用例表能发现它，
是因为期望值由另一条路当场算。

## 稳定性怎么测：样本、判据，以及「不靠多跑」的替代法

「跑两次、比个总数」不能当结论。这里把算术摊开，说明为什么。

**9/22 的 95% 置信区间是 [23%, 61%]** —— 宽 38 个百分点。也就是说 `9/22 vs 9/22`
这种比较，两个数一样只是巧合意义上的「没差别」，任何一边 ±3 次都在噪声里。

要检出「41% → 60%」这样的提升，每组需要 **105 次**运行（α=0.05，power=0.8）；
检出 41% → 70% 也要 42 次。按每题 100 轮、每轮一次调用算，一组 105 次约 6000 万 tokens。
**在有限模型资源下，靠 A/B 大样本选优化点是跑不起的。** 所以：

- `bench.py --reps 2` 的结果只作**观测**，不写进结论；
- 纯净版 / 增强版的 9/22 vs 9/22 同理，只能说明「没看出差别」，不能说明「没有差别」。

### 「稳定」的门槛比想象高

`p` 是单次成功率，`p^k` 是同一题连跑 k 次全过的概率：

| 单次成功率 | k=3 | k=5 | k=8 |
|---|---|---|---|
| 41% | 7% | 1% | 0% |
| 60% | 22% | 8% | 2% |
| 80% | 51% | 33% | 17% |
| 90% | 73% | 59% | 43% |
| 95% | 86% | 77% | 66% |
| 99% | 97% | 95% | 92% |

**要「稳定完成」，单次成功率得在 95% 以上**；把平均分从 41% 提到 60% 仍然是「五次里四次不稳」。
这就把优化目标换掉了：不是把平均分往上抬一点，而是**消灭那些每次都以同样方式失败的模式**。
随机涨落改不了它，确定性 bug 才改得掉它 —— 而确定性 bug 可以在账本里被数出来，不必再问模型。

### 三个离线工具（都不花模型钱）

| 工具 | 回答什么 | 怎么用 |
|---|---|---|
| `ledger_audit.py` | 哪些轮次是白烧的：参数重复、**产物重复**（换措辞问同一件事）、同类报错 | `python ledger_audit.py` |
| `replay_check.py` | 同一个历史决定，在**新规则**下是仍失败还是能被接住（反事实判定） | `python replay_check.py --detail` |
| `test_orch.py` | 编排层改动的单测（引用别名、拆件映射、收口窗口、草稿板） | `python test_orch.py` |

`replay_check.py` 的依据是：账本已经记了「当时它想干什么、当时场景里有什么、它得到了什么」。
这三样足够确定性地回答「这一步本来会不会失败」，不需要再跑一次模型。
它只估计**机械层面的上限**，不预测模型会不会因此变聪明 —— 这个边界必须说清楚。

## 本轮编排层改动（v1.5）：把机械失败从账上抹掉

统计口径：46 次现场运行（`bench_*` / `raw_*`），2658 轮，**195 次报错**。

### 怎么验证这批改动（有限资源下的顺序）

1. **先离线**：`test_orch.py` 全过 + 五道难题的录制回放全部仍 `OK`（`rp_T03/T05/T06/T08/T10`，
   账本链完整、答案键数不变）。这证明改动没有破坏能力上限。
2. **再小样本现场**：同一批题 `--reps 3`，只看**逐题是否 3/3**，不看总分。
   任何一题从「3/3」掉到「2/3」都算回归，先查原因再谈收益。
3. **一次只改一类**：四类病因分开上线，否则分不清是修好了还是被别的东西掩盖了。

## 「几何画面是空的」：那次不是没渲染，是前端崩了

现象：右侧「几何画面」只剩一个破图图标和 `alt="scene"` 的字样，整页停在「未载入」，
但这一轮明明跑完了、`frames/` 里也有 PNG。

诊断（`viz/probe.mjs` 连 CDP 读页面状态）：

```
TypeError: Cannot read properties of undefined (reading 'toFixed')
  at f3 (studio.html:878)
  at digestOf (studio.html:881)
  at renderFeed (studio.html:776)
  at loadRun  (studio.html:725)
```

`select` 对没有三向尺寸的实体会返回 `"dims": [null, null, null]`（**这是合法返回**，不是坏数据），
而摘要函数 `digestOf` 直接 `x.toFixed(3)`。一个 `null` 抛异常 → `renderFeed` 中断 →
`loadRun` 后面的 `renderRight / renderStatus` 全没执行 → 页面停在初始骨架。

初始骨架里那个 `<img id="shot" alt="scene">` **没有 src**，浏览器就画成破图 + alt 文本。
所以「没有几何画面」是两层叠出来的：**渲染崩了**，而且**空态长得像故障**。

修法：

| 改哪 | 改成什么 |
|---|---|
| `digestOf` 的 `f3` | `null` / `NaN` 显示 `?`，不再抛异常（`dims` 里出现 `null` 是正常的） |
| `loadRun` | 五个渲染器各自 `try/catch`：坏数据只坏一块，并提示「账本与答案不受影响」 |
| 几何画面 | 三态显式渲染：有帧 / 进行中 / 未载入，空态写清原因；`img.onerror` 把取不到的地址打出来 |
| 进行中 | `run_agent.live_preview` 每 6 步或 2.5 s 渲染一张 `frames/live.png`（单帧 ~0.25 s），页面轮询刷新 |

回归：`node viz/test_digest.mjs`（6 种少字段返回，含 `dims: [null,null,null]`）。

**顺带纠正一个判断**：之前把「几何画面空白」当成「这一轮没有渲染帧」，
实际上多数时候是这条 JS 崩。判断依据要看 `frames/manifest.json` 有没有内容，
不要看页面那张图 —— 图空可能只是页面挂了。

## 几何画面：从「快照」换成 three.js 实时视图

原来的画面是 `PIL` 手绘的正交投影 + **画家算法**。它有三个改不掉的问题，
都跟"画得好不好看"无关，是**读不出来**的问题：

| 问题 | 表现 | 原因 |
|---|---|---|
| 遮挡会算错 | 家具穿过墙、该挡的地方露出 | 画家算法按三角形深度均值排序，长条三角形必然排错 |
| 视角固定 | 只给 3 个固定偏航角，看不到顶面/背面 | 帧是离线生成好的 PNG |
| 点不中 | 看见一块，不知道它是哪个 sid | 图里没有实体身份 |

**"重不重"实测下来了，答案是不重：**

| 项 | 体积 | 说明 |
|---|---|---|
| 场景 | 20 实体 / 9,245 顶点 / 18,426 三角面 | 赛方模型 + 测试体，固定量级 |
| 几何数据 | **459 KB 原始 / 126 KB gzip** | 扁平 Float32 数组，4 位小数 |
| three.js r149 | 594 KB / **149 KB gzip** | 放 `viz/lib/`，不走 CDN |
| 传输 | 运行中先 `?probe=1` 拿 mtime，变了才取全量 | 800 ms 轮询不会重复拉 460 KB |
| 渲染 | 18k 三角面，集显几百帧；空闲时不跑渲染循环 | 只在 dirty 时画一帧 |

`viz/geom.py` 把场景导成扁平数组（`v` 顶点、`f` 索引、`g` 分组），
前端 `new Float32Array(v)` 直接进 `BufferGeometry`，不需要再 map 一遍。

### 前端做的事

- **拖=转 / 滚=缩放 / 右键或 Shift=平移 / 双击=聚焦**（轨道控制自己写，不引 OrbitControls）
- **点选实体** → 高亮 + 浮层列出「账本里哪几步引用过它」，点步骤号直接跳到那一轮
- **透视墙**：按「厚高比 < 0.5 且薄边 < 0.32 m」识别墙/地/顶，切 FrontSide 剔除背面。
  从外面看是实墙，镜头转进屋里自动看穿——这比 alpha=0.34 的真半透明干净得多
  （半透明会让墙后的家具也变淡，像蒙了层雾）
- **首帧自动定机位**：场景是 18.9 × 4.4 × 5.6 的长条，机位沿长轴偏 30°，
  距离按 `半长轴 / tan(水平半角)` 算，再按投影后的包围盒把画面拉回中心
- **运行中实时更新**：`geom.live_geometry` 每 4 步或 1.5 s 重写 `geom.json`，
  更新时**不重定机位**（否则用户刚转好的视角会被一次次拽回去）

### 每步工具的标注（marks）：不只「现在长什么样」，还画出「这一步做了什么」

`geom.json` 新增 `marks` 字段 —— 每成功执行一步就生成一条三维注解，前端按步骤时间线
（滑块 + ◀▶）叠加到画面上。数据源是 `loop.results[sid]`（**完整原始返回值**，
不是被截断到 300 字的 `obs`），所以能拿到见证点、法向、切面这些精确几何量：

| 工具 | 三维表现 |
|---|---|
| select / pick / merge / clusters / parts | 高亮**焦点实体**（`focus` 列表） |
| distance / rank | 两见证点 + 测量线 + 数值标签 |
| angle | 两根法向短线 + 角度弧 + 度数标签 |
| clearance | 最近两点连线 |
| opening_edge | 洞口底边参考线 |
| collide | 最深穿透点 |
| cut_plane / section | 半透明切面 + 边框 |
| translate / rotate_axis / stretch_axis | 被改实体 |

实现要点：
- `viz/geom.py` 的 `step_marks(loop)` 遍历已成功步骤，从每步完整返回值提取 `focus/markers/lines/arcs/planes`；
  `dump()` 加 `marks` 参数；**收尾 dump 也必须带 marks**（否则会覆盖运行中累积的标注）。
- 前端 `applyMarks()` 在 `marksGroup`（与实体同一 `rotation.x=-90°` 坐标系）里画
  测量线 / 标记球 / 角度弧（`QuadraticBezierCurve3`）/ 切面四边形，标签用 `CanvasTexture` 的 `Sprite`。
- `renderMarkbar()` 渲染时间线 UI；`setMarkStep(i)` 切步 → `applyMarks` + `followFocus`。

### 相机追踪：焦点对象占画面约 75% 且居中，其他构件半透明

- `focusCameraOn(bb)`：`target` 设为焦点包围盒**中心**（焦点居中），距离按**水平 / 竖直两方向
  分别算** —— 每个方向的投影半径 `max(该向尺寸/2, 深度/2)`，除以 `0.75 · tan(halfFov)`，
  取更大的一个。这样任意朝向看过去，焦点包围盒都占约 75% 画面（不裁边、不偏小）。
- `paintHover()` 进入**追踪模式**（有焦点实体时）：焦点实体不透明 + 高亮，
  其余构件半透明（结构 0.22 / 普通 0.45）——焦点从一堆构件里"浮"出来。
  追踪模式与「透视墙」开关独立。
- 用户拖动 / 滚轮 → `userMoved = true` 停自动跟随；点「全景」按钮清零恢复跟随。
- `initMarks()` 里补了 `followFocus()` —— 之前加载完成后相机停在全景视角不跟焦点，这是个 bug。

### 遮罩清除（在跑新轮"没有三维画面"的真因）

`renderView` 出题时会插入 `#geoloading` 遮罩（"正在取几何…"），但 `refreshGeom` 取到几何后
**漏了清除**——三维其实画出来了，只是被半透明白色层盖住，看起来就是"没有三维画面"。
修复：`refreshGeom` 末尾补两行 `remove(#geoloading / #geooverlay)`。

### 踩过的四个坑（都写在注释里了）

1. **`renderer` 赋值位置**：提前赋 `VIEW.renderer = rd` 会让下一次调用以为已初始化，
   相机/网格还没就绪就返回 —— 现在放到初始化最后一行。
2. **水平视角换算**：three 的 `fov` 是竖直角，水平半角必须 `atan(tan(fov/2) * aspect)`。
   写成 `atan(tan(fov/2) * max(0.8, aspect))` 会把距离算大 17%，画面四周全是空白。
3. **z-up → y-up**：`R_x(θ)` 把 `+z` 送到 `(0, -sinθ, cosθ)`，要送到 `+y` 必须 **θ = −90°**。
   写成 +90° 会整个场景上下颠倒（地板在头顶、椅子腿朝天），远看还像正常的。
4. **面板重建丢 canvas**：`renderRight` 每次整块重写 innerHTML，WebGL 的 canvas 跟着被删。
   `renderView` 里检查 `renderer.domElement.isConnected`，掉了就重挂。

## 自然语言整理：把结构化答案写成「题 / 答」

agent 交的答案是结构化键值（`angle_deg: 65.0`），人读起来还要自己在脑子里拼
「哪个键对应题目问的哪件事」。这里用**独立的一轮 LLM**（`run_agent.py` 的
`narrate_answer`）把它们组织成直接回答题目的话——**不重算、不改任何数**，只决定措辞与顺序。
`temperature=0`，一次调用，不重试；失败不影响已跑完的任务。

- 数据源：题目原文（`brief.raw`）+ 已交答案（`values` / `unknowns`）+ 关键步骤意图。
  `insufficient.reason` 也会整理——「为什么做不到」比空转更有价值。
- 产物：`runs/<tag>/answer.md`（Markdown），同时写回 `result.json` 的 `narrative` 字段。
- **控制台打印**：答案**通过审计**（`status == OK`）后，按下面的格式打印，让人直接读结论、
  不用从 JSON 里抠键值：
  ```
  ———— 题目与回答 ————
  题：量出门扇的宽度和高度。
  答：门扇（C011）的高度为 2.03 m；宽度暂取 1.0 m（借用所在洞口净宽）…
  ———————————————————
  ```
  答：只放在首行，回答正文自然缩进（不每行叠一个"答："，否则子标题读着像多条回答）。
- **两个坑**：
  1. 不能直接调 `LLMPolicy._endpoint(_provider(model))`——参数顺序不对；要复用 `LLMPolicy(model)` 实例。
  2. `studio.py` 出题时别把 `title` 拼进 `raw`——否则"题："会印成「题：<title> 题目」答非所问。
     现在 title 单独存 `brief.json`，`compile_brief` 只处理纯题目原文。

## 成本：钱花在哪、怎么省

一次 T01-3（37 轮）的实测，用量由 `run_agent.py` 写进 `result.json` 的 `llm_usage`：

```
prompt 432,794 tok   completion 9,218 tok   calls 37
每轮平均 prompt ≈ 11,700 tok
```

拆开看一次调用的 prompt 构成（进 schema 的部分按字符算，中文约 2 字符/token）：

| 部分 | 字符 | ≈token | 占单次 prompt |
|---|---|---|---|
| **工具参数说明** `params` | 18,042 | 9,021 | **约 74%** |
| 工具一句话描述 `desc` | 6,047 | 3,024 | 约 25% |
| 最近 4 步完整观察（`keep_full=4`，均值 1,634 字符/步） | ~6,500 | ~3,250 | — |
| 卡片 + 历史表 | ~4,300 | ~2,150 | — |

结论很直接：**一半以上的 token 用在「教模型怎么调工具」，不是「它看到的东西」。**
（`pre` / `degrade` / `returns` 不进 schema，`full_specs()` 里已经滤掉，所以那三项不花钱。）

**两层压缩都有开关，不必回退代码**（压缩逻辑与修复逻辑是两件事，回退会把轮次修复、审计改进一起丢掉）：

| 开关 | 关掉的是 | 代价（实测） |
|---|---|---|
| `WB_SCHEMA=full` | 工具说明的「类型 + 一句话」精简，回到原文渲染 | 每调用 prompt +8% |
| `WB_OBS=full` | 观察压缩（预算 5200→48000 字符、不投影、历史保留 4→12 步完整观察） | T09 从 32~65 轮 / 71.5 万 tok 变成 **89 轮 / 188.6 万 tok**（2.6 倍），答案仍对 |

两个开关可以独立设，也可以一起设 —— 这样「压缩前/后」是同一份代码上的两个配置，
账本、报告、验收口径完全一致，对比才有意义。真要物理回到某一版，用
`git worktree add ../pre-terse pre-terse`（tag 见下），比 `git checkout` 来回切干净。

已做（`WB_SCHEMA=full` 可回到原文渲染，便于对照）：

| 做法 | 静态收益 | 实测 |
|---|---|---|
| 参数说明只留「类型 + ≤26 字」，列表参数的引用语法压成「；或写 @步骤.field 引用」 | MEASURE 阶段 schema 26.2k → 22.1k 字符（−16%） | 每调用 prompt 12,429 → 11,431 tok（−8%） |
| 工具描述去掉「前置条件」（写错会被门控拒，拒绝信息本身就够），只留「一句话用途｜失败时｜返回字段名」 | 同上 | 同上 |
| 压缩时**保留单位与默认值**（括号内不切句）：`"float 连通阈值（mm，默认 15）"` → `"float 连通阈值（mm）（默认 15）"`，单位丢了会把 mm 当 m | — | 静态检查：所有参数说明括号配对、无截断单位 |

按阶段拆开看，轮次几乎全花在 IDENTIFY 的 `select` 上：

三处已经做的减轮次，效果差别很大：

| 做法 | 效果 |
|---|---|
| **`assembly` 等工具接受指纹列表**（模型常把 select 的整份返回当 `walls` 传进来，`sorted(dict)` 直接 TypeError，一步失败 → 它再试三遍 → 四轮白烧） | **T01-3 33 → 24 轮（−27%，中位数，三次运行 23/24/24）**，确定性收益 |
| `select` 命中集合与上一步完全相同时提示"换条件没带来新信息"；重复 `load` 同文件直接说"场景没变" | T01-3 未再降；case_C 53（基线 51）—— 因为它在**收窄**候选（12→3→1），那不是空转 |

结论：**剩下的轮次不是编排开销，是搜索成本** —— 画框既不挂在洞口上、也没有现成的分组，
只能在 20 个实体里靠谓词一层层筛。要再降就得给它一个更好的索引（按贴靠的板/墙分组），
那已经接近"替它认对象"，与项目边界冲突，所以停在这里。

**别拿单次对比当结论**：同一张卡、同一模型，原文渲染 20 轮 / 24.8 万 tok / 36 秒，
精简渲染 24 轮 / 27.4 万 tok / 52 秒 —— **轮次波动（±20%）比瘦身收益大**。所以上面采用
「每次调用的 prompt」这个与轮次无关的口径；总 token 只能靠多次运行取中位数比。
两次都算出 65.0°，判据没退化。

优化清单，按 ROI 排：

| 手段 | 预期 | 风险 |
|---|---|---|
| **参数说明瘦身**（`"str  实体清单，或引用字符串（如 @load.solids）"` → `"list 实体或 @引用"`） | 单轮 −5~7k tok，**单题 −40%** | 参数写错率上升；`Bus._coerce` 与工具报错能接住大部分 |
| `keep_full` 4→3，或观察只留关键字段 | 单轮 −1k tok（−8%） | 上下文变薄，可能多问一轮 |
| `assembly` 观察压缩（每族 6 成员 × 9 字段 ≈ 2k 字符） | 单轮 −1k | 判据证据变少 |
| 复核提示提前到 VERIFY 第 1 步 | 轮次 −10% | 少了自我纠错机会 |
| 按题面收窄阶段工具集 | 单轮 −3k | **不做**：等于把题目知识塞进循环 |

另外两笔隐形成本，都已经处理：

- **一次崩溃 = 一次重跑**。`LLMPolicy.decide` 里 `json.loads(fn["arguments"])` 没有容错，
  模型吐一次非法 JSON（少引号/多逗号）整个 run 抛异常退出，前面 30 轮的 token 全废。
  现在记一条 `bad_args` 并返回可修正的提示，继续跑。
- **重复调用**。全量运行里重复调用占 7%；同工具同参数第 2 次起就有提示，第 3 次命中缓存不再重算，
  `assembly` 另有按「墙 + 参数 + 场景代号」的记忆（`items` 只影响 loose 清单）。
- **「差一口气」的整轮浪费**，今天补了两处：模型给出非法 JSON 参数（少引号/多个逗号）现在只记一步
  可修正的错误，不再抛异常退出；模型把结论写在正文而不给 tool_call 时，回它一句「用工具提交」再问
  一次（只重试一次）。前者原来是崩一次 = 重跑一次（44 万 token），后者实测真发生过 —— 65.0° 算对了，
  却整轮判 `INSUFFICIENT_EVIDENCE`。

## 观察压缩：压精度，不压判据

一次 `load` 的 20 个实体原样 11.6k 字符，全给会占掉每轮 prompt 的大半；全压又会让模型
「看得见 n=20、看不见明细」，转而把同类合并汇报（T09 曾经只覆盖 6/16）。所以压缩只做两件事，
都有明确的例外：

| 做法 | 为什么安全 | 例外（不压） |
|---|---|---|
| 数值压到 **3 位小数**（`sch.SLIM_ND`） | 几何判据的分辨率是毫米，第 4 位起是浮点噪声 | 审计按**同一精度**比对：模型照抄「看见的 0.523」而真值是 0.523074，容差若按 1e-6 算就会稳定判它编造（T09 连拒三次 `AUDIT_FAILED`） |
| 批量结果压成「一行一个实体」，只留 14 个键 | 这 14 个键覆盖判据所需：三边 `d0/d1/d2` + 世界轴跨度 `sx/sy/sz` + 板厚 + 长边轴 + 落地标高 + 中心 + 填充率 | 取 **≤4 件**时不压；`select(fields=[...])` 点名要哪些字段时不压 |

几处踩过的坑，都写在代码注释里：

- **`dims` 与 `sx/sy/sz` 看似重复，其实各有各的用处**。`dims` 是任务卡要的交卷字段；
  `sx/sy/sz` 才回答「这面墙沿哪根轴立着、厚度是哪个方向」。只给前者的那一版，模型只能自己
  推轴向，推出来的数不在任何工具返回里 → 审计判「无法追溯」→ 它交了空答案或只有一句话的答案。
- **压缩后要给出「怎么拿回被压掉的东西」**。观察里写明「已压成一行一个实体（只留 …）」，
  `select(fields=…)` 与小集合直通就是那条路；没有它，模型会反复用同一参数取全集
  （实测同一签名连调 9 次 → 判停滞）。
- **空答案必须拒**。审计原本只管「数字有没有出处」，于是 `{"values": {}}` 天然通过，状态还是
  绿色的 `OK`。现在空 `values` 走统一拒绝出口；三次都空判 `AUDIT_FAILED` —— 量不出来应该走
  `declare_insufficient`，那是诚实的终态。
- **只交 `note` 也是绕路**。空答案被堵之后，模型改交 `{"note": "见 entities / multi_part / …"}`
  —— 它以为前面已经写过，实际一次都没交。现在 `values` 只含 `note/notes/说明` 这类自述字段时
  直接拒；`{"has_hole": "否"}` 这种真正的短字符串答案不受影响。

预算与字段是配套的：14 个键 ×20 个实体 ≈ 3.6k 字符，所以观察预算从 5200 提到 6800
（投影阈值 = 预算 × 0.62 ≈ 4216）。宁可每轮多几百 token，也不要让模型拿着不全的字段去猜 ——
猜出来的数过不了审计，代价是一次重跑。

## 已知限制（写在明处）

1. **扫掠是「逐位置离散 + 边界二分」，不是解析 CCD** —— 窄于粗扫步长的孤立接触可能漏检，
   所以返回值里必须带上步长与二分精度。连续段和重叠段不会漏（每段内还做了 K=9 采样）。
2. **写层只做平面切割，不做一般布尔** —— `cut_plane` 是半空间裁剪。08 / 10 都不需要布尔
   （开门是刚体转动、对接是刚体平移，两实体始终保持分离或相切），但若出现「必须互相挖去」
   的题，现在只能报 `declare_insufficient`。
3. **写层的锚点与位移按世界轴写** —— `stretch_axis` 的锚点、`translate` 的 delta 都是米制世界坐标。
   跑 `compare_edits.py` 可以看到后果：T-07 绕竖轴转 90° 仍一致（它只动 z），
   而 T-05 / T-06 转 90° 后不一致并被判 `AUDIT_FAILED` —— 房间的「左右」不再对应世界 x。
   要修得让锚点跟场景参照系走；**目前的行为是可接受的：失败被审计抓到，而不是悄悄给出错模型**。
4. **圆孔按多边形近似** —— 48 段，面积精确到 1e-6，但外接方框宽 1.5828 而非 πr 的 1.5799；追求解析圆需要曲面拟合。
5. **曲面只有球能做解析拟合** —— `fit_sphere` 用代数最小二乘解 `|p|² = 2c·p + (r²−|c|²)`，
   报拟合半径与 `roundness`（最大残差/半径，本例 2.0e-6）。柱与锥仍只能给「光滑闭合曲面」，
   给不出轴、锥度与解析半径。
6. **`principal_frame` 只处理绕竖轴旋转** —— 它把 z′ 固定为世界 Z；真正倾斜（斜墙、坡屋面）会落进 `up_confident=false` 分支。
7. **`clusters` 的边界依赖主参照系** —— 已在主参照系下聚类（世界轴 AABB 只是真实距离的下界，
   旋转时最多膨胀 √2 倍：45° 时火箭与房间的间隙从 2.8 m 塌到 0.71 m，三簇并成一簇）。
   残留风险：若场景没有显著平面朝向（全曲面场景），`frame.used` 会退回 `world` 并标注，
   此时判据退化到世界轴。`consistency.agree=false` 就是给 agent 的显式信号。
8. **LLM 策略尚未稳定收敛到「提交答案」** —— 见上一节的实测：能走完工具链、能提交，
   但审计或推断上的一个小错就可能让它退回验证、最后停在 `STALLED` / `INSUFFICIENT_EVIDENCE`。
   控制台只有这一条路径，失败会如实标出来，不伪装成成功。
9. **`distance` 对相交网格返回 0**，不区分「接触 / 穿透 / 含于内部」。要分开得再看两个量：
   `collide` 的 `n_pierce`（>0 即穿插，如把手嵌在门扇里 38 对穿刺、深 0.01 m）与
   `contact_area`（>0 即贴合，如四只脚贴地 0.0121 m²）。**单看距离一项，这三种情形长得一样。**
10. **`FBX` / `.blend` 不支持**，需离线转 OBJ。
11. **`contains` 的 `plane` 只支持轴对齐的三个平面** —— `xy` / `xz` / `yz`。房间若整体旋转，
   得改成「占地多边形是否在楼层平面多边形内」的一般判定；现在会退化成包围盒比较。
12. **控制台没有「离线」这条退路** —— 它只收原话和模型，决策必须现场做。所以在线路径的不收敛
   就是控制台的不收敛，没有兜底。这是当前最该补的一块：让在线路径在预算内稳定收口；
   而不是给它配一份预先录好的答案 —— 那等于把「会不会解」换成了「背没背过」。
13. **读层四题的验收读的是 `result.json` 里的数字** —— 它们没有产物文件可读，所以
   「验收只认磁盘文件」这条纪律在它们身上退一步。补偿办法是换算法：每一条都用原理不同的
   方法重算（球冠解析式、球缺闭式解、行列式体积），不比对叙述。仍然没有覆盖的是
   **文字结论**（例如「这面墙没有洞」这类定性判断）—— 那部分只能靠 `wall_openings` 里的
   数字自证，验收不会替它说话。
14. **「唯一命中」不保证唯一正确** —— 判据（`select` 的 where）是模型现场写的，系统只强制
   「命中数 = 1」，不强制「命中的就是那个角色」。这条曾把第 01 题第 4 问卡住：房间绕竖轴转 90°
   后再问，门洞与椅子都唯一命中，方位命题却写歪（早先是两个距离对调，后来变成「距离对、标签反」）。
   **现在关掉了**，靠的不是模型变强，是三件事：
   a) 任务卡把口径钉成**有向轴**（右向＝门洞墙→它对面；后向＝开口→有墙），不再用「坐标较小的
      一侧」这种旋转后会自动翻面的说法；
   b) 答案必须交**带符号的偏移**（`offset_along_right_m` / `offset_along_back_m`），左/右、前/后
      两个标签**由符号翻译**，不另做判断 —— 标签与符号矛盾会被验收单独判出来；
   c) 指纹给 `h_long_axis`，`select(probe=true)` 给反例与余量，让判据能自证。
   仍然会错的是**对象指代**：问「画框」时模型一度选到门上的横档、后来又选到窗（`runs/cases.md`
   的 C 例，编号 C015 才是画框）。这属于「题面指谁」而不是「几何量算错」。解法是两步，现在都做了：
   `assembly` 用**接触 + 连通**把「谁挂在哪个洞口上」算成族（拓扑关系，开着也成立）；
   编排层再用族的 `facts`（grounded / 下框 / 扇）把语义范围**收窄**成
   `{窗,无法区分}` / `{落地窗,无法区分}` / `{门,无法区分}` / `{门,落地窗,无法区分}` 四档之一，
   写进那一步的 `_scope`，并明确「未列入任何族的构件 = 非门窗」。
   C 例因此从 96 轮（37 次 `select` 硬筛）降到 51 轮，而且走的是族。
   **仍然允许「无法区分」** —— 落地窗、固定窗、平开窗、有门槛的门这四类反例都写在 SYSTEM 4c 里，
   判不出来就承认，不拿尺寸凑。
