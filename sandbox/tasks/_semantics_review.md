# 语义分歧评估表

> 目的：找出所有赛题里"参照物可能有多个候选、需 agent 自行判别"的点，确认每个分歧点
> 是否有**唯一客观答案**、现有工具能否判出来。这是"让 agent 具备判断力"的设计输入。
>
> 结论先行：10 个题里**真正的语义分歧只有 4 处**，且**全部有客观几何判据、现有工具就能判**。
> agent 在 `live_1126_143151` 里答错（夹角 25°≠65°），不是工具不够，是**推理链缺一步**。

## 一、分歧清单

| 题 | 位置 | 分歧 | 客观判据 | 现有工具 | agent 能否判 |
|---|---|---|---|---|---|
| T01_2 | 窗框 | C013 vs C014 | 厚 0.24m=框 / 0.02m=玻璃 | `select(dims)` | ✅ 能 |
| T01_2 | 画框 | C015 vs C016 | 厚 0.08m=框 / 0.025m=画心 | `select(dims)` | ✅ 能 |
| T01_3 | 门所在墙 | C005 vs C006 | grounded=True=门洞 / False=窗洞 | `openings` | ✅ 能 |
| T06 | 窗框 | 同 T01_2 | 同上 | 同上 | ✅ 能 |

## 二、其他题为什么无分歧

- **T01_1 / T03 / T04 / T05 / T08**：参照物（门洞 C012、椅子 C017、地板、墙）都是唯一实体，
  题目措辞已经把方向/参照说清楚（"左墙内侧""地板前边界""门洞下沿"），无多义。
- **T02 / T07 / T10**：涉及的是不同模型组（球与正方体、火箭与发射台），实体数少、
  形状差异大（球/立方体、火箭/平台），题目要求"自行分组"本身就是考识别，无歧义。
- **T09**：整题就是考"如何用几何特征识别门窗画框椅子"，判据（grounded / 厚度 / 贴合关系）
  题目已经给全，是识别能力的**正向考核**，不是要规避的分歧。

## 三、判据的几何本质（可复用的三条）

这三条能覆盖所有 4 处分歧，都是**纯几何**、不依赖名称：

1. **厚度判别（框 vs 透光件）**
   - 规则：一对叠放的薄板件，厚的（≥ 0.05m）是框/结构，薄的（< 0.05m）是玻璃/画心
   - 工具：`select([sid], fields=['dims'])` → 取 `min(dims)`
   - 阈值：0.05m 是工程经验值（窗框 10-15cm、画框 5-8cm、玻璃 3-5mm、画心 2-3cm）

2. **落地判别（门洞 vs 窗洞）**
   - 规则：`grounded=True`（sill_z=0）是门洞，`grounded=False`（sill_z>0）是窗洞
   - 工具：`openings(walls=[sid])` → 看 `grounded` 字段
   - 物理意义：门要人走、必须落地；窗在墙上、有窗台

3. **归属判别（部件属于哪面墙）**
   - 规则：部件（门扇/窗框/画框）的法向与哪面墙的法向平行，且位置在该墙平面内，就属于该墙
   - 工具：`principal_frame` 或 `select(dominant_dirs)`
   - 用途：T01_3 要判"门所在墙"，先用量门扇法向、再比对两面墙法向

## 四、agent 在 143151 里为什么错（复盘）

题目：T01_3（门扇与门所在墙面的较小夹角）

**agent 的调用序列**（从 `runs/live_1126_143151/steps.json`）：

```
1. select(items=[C011], probe='dominant_dirs') → 门扇法向 n=(0.91, 0.42, 0)
2. angle(a='C011', b='C006', kind='plane')     → 25°  ← 直接用了 C006
3. answer(angle_deg=25.0, ...)
```

**缺的一步**：没有先查 `openings(C005)` 和 `openings(C006)`，确认哪个是门洞（grounded=True）。

**如果它查了**，会看到：
```
C005 opening: width=1.0, height=2.1, grounded=True,  sill_z=0.0  ← 这是门
C006 opening: width=1.4, height=1.4, grounded=False, sill_z=0.9  ← 这是窗
```
然后就会选 C005，`angle(C011, C005)` 返回 **65°**（正确答案）。

## 五、编排改进方向（不添加新工具）

改进的目标：**在不替 agent 思考的前提下，让它多走一步"定位参照物"的验证**。

### 方案 A：通用 audit 约束（推荐）

在 `agent/loop.py` 的 `audit_answer()` 里加一条通用检查：

> 若 `answer.values` 里提交了"门/窗/框"相关量，且账本里没有对应的 `openings` 或
> `select(dims)` 调用，则驳回并提示：
> "提交了门窗类量但未验证参照物身份。请先调用 `openings` 确认门洞（grounded=True）
> 和窗洞（grounded=False），或 `select(dims)` 区分框（厚）与玻璃（薄）。"

优点：
- 不针对特定题（T01_3、T06、T09 都受益）
- 只加约束、不替思考（agent 仍需自己判断哪个 grounded=True）
- 复用现有工具（openings、select）

缺点：
- 可能过于宽泛（不是所有门窗量都需要验证身份，比如 T01_1 的门洞 C012 是唯一实体）

### 方案 B：题目分类驱动的强制路径

在 `compile_brief()` 阶段分析题目措辞，如果含"门扇与墙夹角"、"窗框距离"等关键词，
在 `IDENTIFY` 阶段强制要求调用 `openings` + `assembly`。

优点：精准针对高风险题
缺点：
- 关键词匹配脆弱（自然语言变化多）
- 容易退化成"针对特定题的硬编码"，违反"不针对某题写代码"的红线

### 方案 C：VERIFY 阶段强制复核

在 `VERIFY` 阶段，如果 agent 提交的 `entities` 字段含"wall"/"frame"/"glass"，
强制要求先调一次 `openings` 或 `select(dims)` 验证，才能交 answer。

优点：与现有阶段划分一致
缺点：VERIFY 已经很拥挤（要核数值、见证点、单位），再加可能压垮预算

## 六、推荐路径

**先做方案 A（通用 audit 约束）**，理由：

1. 最少侵入（只加一条 audit 规则，不改阶段/工具）
2. 通用性最强（覆盖所有门窗量，不特化到某题）
3. 与现有纪律一致（账本里已有"提交前必须有可复核的识别结果"，这只是加强"可复核"的定义）

具体实现位置：`agent/loop.py` 的 `audit_answer()` 方法，加一条规则：

```python
# 若提交了门窗类量（键名含 door/window/frame/leaf/wall），但账本里
# 没有对应的 openings 或 select(dims) 调用，驳回一次并提示。
# 只拒一次，第二次放过（避免死循环，同 measured_board 的兜底逻辑）。
```

预期效果：
- T01_3 这类题，agent 第一次交答案时会被驳回，被迫去查 `openings`
- 查完后看到 grounded=True/False，就会选对墙，第二次交答案时审计放行
- 成本：每题多 1-2 轮（调 openings + 重新交答案），可接受

## 七、测试方案

1. 用 `live_1126_143151` 的 brief（T01_3 类题）重跑一次，观察：
   - agent 是否在第一次 answer 时被驳回
   - 驳回理由是否清晰（提示查 openings）
   - agent 第二次是否选对了 C005
   - 最终 angle_deg 是否变成 65°

2. 跑 `test_orch.py` 确保 audit 规则没破坏现有测试

3. 跑 `bench.py --strict`（如果支持）验证 OK 率是否提升（T01_3 从错变对）

## 八、风险与缓解

| 风险 | 概率 | 缓解 |
|---|---|---|
| audit 规则过于宽泛，驳回不该驳回的题 | 中 | 键名过滤严格（只匹配 door/window/frame/leaf/wall），不匹配 angle/distance 等通用量 |
| agent 被驳回后仍然选错墙 | 低 | 驳回理由明确指出"查 grounded"，agent 照做就能选对 |
| 增加轮次导致预算耗尽 | 低 | 只拒一次，第二次放过（同 measured_board 兜底） |
| 破坏其他题的测试 | 低 | test_orch 有 29 个用例，跑一遍即可验证 |

## 九、总结

- **语义分歧只有 4 处**，全部有客观判据（厚度/落地/法向），现有工具就能判
- **agent 答错的根因**不是工具不够，是推理链缺一步（没验证参照物身份）
- **改进方向**：在 audit 层加通用约束，要求门窗类量提交前必须验证参照物
- **不添加新工具、不针对特定题、不替 agent 思考**——只是让它多走一步验证
